# UDS CLI Next, NextMode, and Bundles Next research

**Status snapshot: 2026-09-02.** This note uses published UDS documentation and Defense Unicorns' public source, accepted architecture decisions, releases, and pull requests. Statements marked **[Inference]** are deductions rather than an announced product guarantee.

## Executive finding

UDS CLI Next is the next-generation UDS CLI implementation, but it is currently an **alpha preview** selected with the `NextMode` feature flag; Legacy is still the default, and existing `uds-bundle.yaml` workflows continue to run in Legacy mode. The published v0.36 reference says Next is planned to become the beta default and Legacy is to be removed after a beta migration window. [UDS CLI Next Mode reference](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/) · [v0.36.0 release](https://github.com/defenseunicorns/uds-cli/releases/tag/v0.36.0)

There is no compatibility adapter in Next for a legacy YAML definition or artifact: the accepted architecture decision says existing `uds-bundle.yaml` bundles must be migrated and that a migration tool was planned separately. **[Inference]** A legacy bundle therefore remains a Legacy-mode deployment until its source has been deliberately converted and rebuilt as a Next artifact; converting a tarball alone is not a supported path. [Bundles Next ADR — consequences](https://github.com/defenseunicorns/uds-cli/blob/main/docs/adr/0001-bundles-next-spec.md#consequences) · [Next migration guide proposal — known differences](https://github.com/defenseunicorns/uds-cli/blob/1db1ed3587f81e48bdfaa6c3d22d5fc7893c1ed5/docs/how-to-guides/migrate-v1-to-next.mdx#known-differences-and-gaps)

## Terminology and availability

| Term | Meaning and current status |
| --- | --- |
| **UDS CLI Next** | The next-generation implementation and command tree in the same `uds` binary. The accepted coexistence decision keeps Legacy isolated under `internal/legacy` and `pkg/legacy`, while Next occupies canonical paths; `NextMode` selects the tree. It is alpha, while Legacy is the default. [Coexistence ADR](https://github.com/defenseunicorns/uds-cli/blob/main/docs/adr/legacy/0010-legacy-next-coexistence.md) |
| **NextMode** | Per-command feature flag, enabled as `CLI_FEATURES=NextMode=true uds …` or `uds --features=NextMode=true …`. Next bundle definitions must be named `bundle.uds.hcl`. [NextMode reference — enabling](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#enabling-next-mode) |
| **Better Bundles** | Historical/design name for the bundle redesign. The accepted ADR changelog says it was renamed to **Bundles Next** on 2026-08-27, and the merged terminology PR says the old term was retired; the versioned v0.36 documentation still uses the old heading. Treat “BetterBundles” as the predecessor name, not a separately enabled CLI mode or a bundle format. [Bundles Next ADR](https://github.com/defenseunicorns/uds-cli/blob/main/docs/adr/0001-bundles-next-spec.md) · [merged terminology PR #1524](https://github.com/defenseunicorns/uds-cli/pull/1524) · [v0.36 NextMode reference](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#better-bundles-design) |

## What changes in the bundle workflow

Legacy authors use `uds-bundle.yaml`, `uds create`, `uds deploy`, and bespoke package/component `overrides`. Next authors use an HCL2 `bundle.uds.hcl` with `package "<id>"` blocks, then use `uds bundle dev deploy`, `uds bundle create`, `uds bundle deploy`, `push`, `pull`, `inspect`, `remove`, `sign`, `verify`, and `reconfigure` as the corresponding bundle surface. Package dependency edges use `depends_on`; independent packages in a dependency level may deploy concurrently. [NextMode command reference](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#cli-commands) · [Bundles Next ADR — HCL definition](https://github.com/defenseunicorns/uds-cli/blob/main/docs/adr/0001-bundles-next-spec.md#bundle-definition-hcl) · [NextMode deployment behavior](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#deploying-a-bundle)

Next separates configuration by lifecycle. `defaults.uds.hcl` is a lowest-priority defaults layer carried in a created artifact, while `config.uds.hcl` supplies deploy-time variables and options through `--config`; values files can template those variables and top-level scalar variables are also supplied to Zarf substitutions. `uds bundle reconfigure` can make a derivative artifact with changed defaults without rebuilding package content. [NextMode configuration reference](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#deploy-time-configuration) · [defaults](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#bundle-level-variable-defaults) · [reconfigure](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#reconfiguring-a-bundle)

Package verification becomes explicit in each HCL package block: the author must configure exactly one `public_key` or `keyless` method, or deliberately set `verify = false`. Package `namespace` and `values_files` are direct Zarf-native inputs; this replaces the bundle-level Helm `overrides` mechanism. [NextMode package verification](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#package-signature-verification) · [Bundles Next ADR — Zarf-native inputs](https://github.com/defenseunicorns/uds-cli/blob/main/docs/adr/0001-bundles-next-spec.md#bundleuds-hcl)

## Bundles Next model and compatibility implications

A Next bundle is a self-contained OCI-oriented artifact: remote OCI packages are copied into an internal OCI layout, local Zarf tarballs are normalized into that layout, and package manifests/layers are represented explicitly. The published v0.36 design shows an architecture-selecting root index and single-architecture child artifacts with `application/vnd.defenseunicorns.uds.bundle.v1`; the accepted ADR additionally records bundle-specific config/layer media types and content-addressed blob reuse. [published artifact layout](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#better-bundles-design) · [accepted OCI structure](https://github.com/defenseunicorns/uds-cli/blob/main/docs/adr/0001-bundles-next-spec.md#oci-structure)

The compatibility break is intentional: YAML's limitations, duplicated overrides, indirect OCI blobs, and lack of a bundle media type were documented as the motivation. The trade-off is that a legacy `UDSBundle` is not a Next input; its package interface must be expressed through HCL and the Zarf packages' native namespace/value mappings. [Bundles Next ADR — context and decision](https://github.com/defenseunicorns/uds-cli/blob/main/docs/adr/0001-bundles-next-spec.md#context)

## Historical conversion sketch (not a Neutrino bundle)

The following `bundles/core/uds-bundle.yaml` / `gs-core` example describes a separate bundle-authoring project, not a file or workflow in Neutrino. Treat it as a dated migration sketch; Neutrino's bundle fixtures are under [`src/test/bundles/`](../../../src/test/bundles/).

1. **Preserve the Legacy path first.** Keep `bundles/core/uds-bundle.yaml` and current `uds create`/`uds deploy` automation as the deployable baseline while Next remains alpha. Create the Next definition in a separate directory so the two workflows can be tested independently. Legacy is still default and the published documentation explicitly says its YAML workflow continues to work. [NextMode mode status](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#mode-status)
2. **Translate bundle identity and packages.** Create `next/bundle.uds.hcl` with `uds { bundle_api_version = "uds.dev/v1alpha1" }`, a `metadata` block for `gs-core`, and one `package "<id>"` block per current package. Combine each legacy `repository` and `ref` into `source = "oci://<repository>:<ref>"`; translate `optionalComponents` to `optional_components`. Architecture moves to `--architecture` or the Next config options rather than metadata. [Next HCL schema](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#bundle-file-structure) · [proposed v1-to-Next field mapping](https://github.com/defenseunicorns/uds-cli/blob/1db1ed3587f81e48bdfaa6c3d22d5fc7893c1ed5/docs/how-to-guides/migrate-v1-to-next.mdx#convert-the-bundle-definition)
3. **Rebuild configuration at the package boundary.** Translate each current `keylessVerification` into `signature_verification { keyless { … } }` using its certificate identity and issuer. Replace every legacy `overrides` tree with per-package `values_files`, then ensure the target Zarf package has matching chart value mappings; use package `namespace` only where one namespace applies to the whole package. Put stable build defaults in `defaults.uds.hcl` and environment-specific values/options in `config.uds.hcl`. [Next verification configuration](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#package-signature-verification) · [proposed overrides/config migration](https://github.com/defenseunicorns/uds-cli/blob/1db1ed3587f81e48bdfaa6c3d22d5fc7893c1ed5/docs/how-to-guides/migrate-v1-to-next.mdx#replace-component-overrides-with-values-files)
4. **Make dependencies explicit.** Add `depends_on` only after preserving the current deployment constraints; Next uses it to form deployment levels and parallelizes packages that do not depend on one another. **[Inference]** For this large infrastructure bundle, begin conservatively with known ordering (for example, initialization and foundational services before dependents), then relax only after non-production verification. [Next dependency behavior](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#deploying-a-bundle) · [Bundles Next `depends_on`](https://github.com/defenseunicorns/uds-cli/blob/main/docs/adr/0001-bundles-next-spec.md#bundleuds-hcl)
5. **Exercise, build, sign, and deploy.** First run `CLI_FEATURES=NextMode=true uds bundle dev deploy ./next --config ./next/config.uds.hcl` on a non-production cluster. Then create a signed artifact, push it to the intended OCI registry, and deploy the artifact with its config and verification material. Development deployment reads source directly and therefore lacks artifact provenance and bundle-signature verification; use the created-artifact flow for integrity-sensitive deployment. [NextMode quick start](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#bundle-quick-start) · [proposed migration workflow](https://github.com/defenseunicorns/uds-cli/blob/1db1ed3587f81e48bdfaa6c3d22d5fc7893c1ed5/docs/how-to-guides/migrate-v1-to-next.mdx#test-create-and-deploy-the-next-artifact)

## Caveats and unresolved release status

- **Do not treat alpha as a transparent upgrade.** Command coverage is still expanding. Next is only planned—not yet committed in a released beta—to become the default, and Legacy removal is scheduled only after a future beta migration window. [NextMode status](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#mode-status) · [coexistence ADR](https://github.com/defenseunicorns/uds-cli/blob/main/docs/adr/legacy/0010-legacy-next-coexistence.md)
- **The official-looking migration guide is not released documentation yet.** Its source is in open [PR #1531](https://github.com/defenseunicorns/uds-cli/pull/1531), so its detailed command/field mapping is useful first-party proposal evidence but not a merged product commitment. The accepted ADR is stronger evidence for the architectural break and format direction. [PR #1531](https://github.com/defenseunicorns/uds-cli/pull/1531) · [accepted ADR](https://github.com/defenseunicorns/uds-cli/blob/main/docs/adr/0001-bundles-next-spec.md)
- **Unsigned local workflows deliberately reduce protection.** The documented alpha quick start requires both `--unsigned` at create time and `--skip-signature-verification` at deploy time when no signing is configured. Use those switches only for intentional local/non-production testing; signed artifacts plus verification are the migration target for registry or production use. [NextMode quick start](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#bundle-quick-start) · [bundle signing/verification](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#signing-and-verifying-bundle-artifacts)
- **Some v1 capabilities have no Next equivalent in the proposed migration guide:** `imports`/`exports`, `uds logs`, `uds list`, deploy `--resume`, `--retries`, `--force-conflicts`, and certain v1 inspect views. `bundle remove` requires a local HCL definition rather than an artifact or OCI reference, so retain the converted source directory. Keep dependent workflows in Legacy mode until their Next replacement is available. [proposed known differences](https://github.com/defenseunicorns/uds-cli/blob/1db1ed3587f81e48bdfaa6c3d22d5fc7893c1ed5/docs/how-to-guides/migrate-v1-to-next.mdx#known-differences-and-gaps)

## Decision summary

Adopt Next as a **parallel, source-level migration**, not an in-place artifact upgrade: preserve the current Legacy bundle, translate it into an HCL/Zarf-native Next bundle, prove it in non-production, and only then publish signed OCI artifacts. This sequencing follows the documented alpha coexistence model and avoids assuming a compatibility or conversion facility that the accepted design explicitly does not provide. [NextMode status](https://docs.defenseunicorns.com/cli/v0-36/reference/next-mode/#mode-status) · [Bundles Next ADR — consequences](https://github.com/defenseunicorns/uds-cli/blob/main/docs/adr/0001-bundles-next-spec.md#consequences)
