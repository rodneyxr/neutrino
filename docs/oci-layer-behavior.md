# OCI layers in UDS bundles, Zarf packages, Helm charts, and images

## Scope and evidence

This note distinguishes **the OCI standards** from **the layouts implemented by this checkout**.  The checkout evidence is pinned to UDS CLI commit [`1787dd331bb062c38df24373414e6bfece3c61c9`](https://github.com/defenseunicorns/uds-cli/tree/1787dd331bb062c38df24373414e6bfece3c61c9) and its declared dependencies: Zarf `v0.82.0`, OCI Image Spec `v1.1.1`, and Helm `v4.2.0` (the Helm OCI source references below use the compatible, independently versioned `v3.19.0` implementation where the constants and pull behavior are explicit). All external references are specifications, official documentation, or upstream project source.

## OCI: what can be discovered before payload transfer

An OCI **index** is a JSON manifest whose descriptors select one or more image manifests (and may include platform metadata). An OCI **image manifest** is a JSON document containing a required `config` descriptor and an ordered array of `layers` descriptors. A descriptor carries at least media type, content digest, and byte size; it identifies bytes, not an application-level file. This graph is the authoritative inventory for a client: inspect it before choosing which referenced bytes to fetch. [OCI Image Manifest v1.1.1](https://github.com/opencontainers/image-spec/blob/v1.1.1/manifest.md), [OCI Image Index v1.1.1](https://github.com/opencontainers/image-spec/blob/v1.1.1/image-index.md), and [Descriptor v1.1.1](https://github.com/opencontainers/image-spec/blob/v1.1.1/descriptor.md).

For a remote registry, the Distribution Spec separates the small manifest request from digest-addressed blob requests:

* `GET /v2/<repository>/manifests/<tag-or-digest>` obtains a manifest. The client supplies accepted manifest media types, verifies a digest-addressed manifest response, and can therefore select an index child before fetching that child’s payload. [Distribution Spec v1.1.1, “Pulling manifests”](https://github.com/opencontainers/distribution-spec/blob/v1.1.1/spec.md#pulling-manifests)
* `GET /v2/<repository>/blobs/<digest>` retrieves exactly one selected blob; `HEAD` checks a manifest/blob and normally supplies its digest and byte size. The client should verify the selected response against the descriptor digest. [Distribution Spec v1.1.1, “Pulling blobs” and “Checking if content exists”](https://github.com/opencontainers/distribution-spec/blob/v1.1.1/spec.md#pulling-blobs)
* `Range` is recommended for resuming a blob transfer. It is **not** a standard operation for extracting a named file from an opaque layer: a range merely returns bytes from that one blob, and the registry does not interpret tar/gzip/zstd contents. Thus selection is descriptor/blob-granular, not file-granular inside a selected layer. [Distribution Spec v1.1.1](https://github.com/opencontainers/distribution-spec/blob/v1.1.1/spec.md#pulling-blobs); [OCI layer format v1.1.1](https://github.com/opencontainers/image-spec/blob/v1.1.1/layer.md).

An OCI **image layout** is the local representation of this same graph: `oci-layout`, `index.json`, and descriptor content under `blobs/<algorithm>/<encoded-digest>`. A layout may intentionally omit a referenced blob when the blob is expected to be available from an external content store, so `index.json`/manifests alone are not proof that every payload is locally present. The specification also describes a tar archive as a transport for a layout; that does not create a standard random-access index inside a compressed archive. [OCI Image Layout v1.1.1](https://github.com/opencontainers/image-spec/blob/v1.1.1/image-layout.md).

## Helm OCI charts and values

A Helm chart published to an OCI registry is an OCI manifest, not a container image. Helm’s registry constants assign the chart metadata config `application/vnd.cncf.helm.config.v1+json`, the packaged-chart layer `application/vnd.cncf.helm.chart.content.v1.tar+gzip`, and an optional provenance layer `application/vnd.cncf.helm.chart.provenance.v1.prov`. [Helm v3.19.0 registry constants](https://github.com/helm/helm/blob/v3.19.0/pkg/registry/constants.go). Helm’s official registry documentation also establishes OCI registries as a chart distribution mechanism. [Helm documentation: OCI-based registries](https://helm.sh/docs/topics/registries/).

`values.yaml` is a file in the chart archive, alongside `Chart.yaml`, templates, dependencies, and optional `values.schema.json`; it is **not** the OCI config. Helm’s loader recognizes `values.yaml` and `values.schema.json` only after loading the chart archive. [Helm v3.19.0 chart loader](https://github.com/helm/helm/blob/v3.19.0/pkg/chart/loader/load.go). Therefore a client may fetch the chart manifest/config first and omit provenance, but must transfer the complete chart-content layer and decompress it to read `values.yaml`. It cannot ask an OCI registry for `values.yaml` alone.

## Zarf package layout (Zarf v0.82.0)

### Local package archive

A file-format Zarf package is a compressed archive of the assembled package directory. Its fixed top-level names include `zarf.yaml`, `checksums.txt`, `images`, `components`, `zarf-sbom`, and `values.yaml`/`values.schema.json`; `images` itself contains the nested OCI layout (`images/oci-layout`, `images/index.json`, and `images/blobs/sha256`). [Zarf layout constants](https://github.com/zarf-dev/zarf/blob/v0.82.0/src/pkg/packager/layout/layout.go); [archive implementation](https://github.com/zarf-dev/zarf/blob/v0.82.0/src/pkg/packager/layout/package.go#L616-L658).

The outer archive is an archive transport, not a registry-addressable descriptor graph. A local inspector can enumerate/extract metadata and chart files without materializing image files, but its I/O behavior depends on its archive reader and compression: it must at least read/decompress through entries it reaches. The Zarf archive writer supplies no OCI-level promise that non-image files occupy a particular prefix. [Zarf archive implementation](https://github.com/zarf-dev/zarf/blob/v0.82.0/src/pkg/packager/layout/package.go#L616-L658).

### Remote OCI package

For OCI publication, Zarf computes one custom layer descriptor per file in the assembled package directory. Each descriptor uses `application/vnd.zarf.layer.v1.blob` and carries the package-relative pathname in `org.opencontainers.image.title`; it builds an OCI manifest with those layers and a separately serialized package JSON config of media type `application/vnd.zarf.config.v1+json`. That means `zarf.yaml`, component data (including charts and values), `images/index.json`, and every file below `images/blobs/sha256/` are separately addressable package-layer blobs. [Zarf OCI layout assembly](https://github.com/zarf-dev/zarf/blob/v0.82.0/src/pkg/packager/layout/oci.go#L31-L35), [descriptor creation and manifest packing](https://github.com/zarf-dev/zarf/blob/v0.82.0/src/pkg/packager/layout/oci.go#L102-L225), [package file walk](https://github.com/zarf-dev/zarf/blob/v0.82.0/src/pkg/packager/layout/package.go#L661-L680).

The embedded container images remain a second OCI graph stored as package files: `images/index.json` points to image manifests, and `images/blobs/sha256/<digest>` holds those manifests, image configs, and compressed filesystem layers. Consequently, the outer Zarf package manifest is sufficient to identify and omit the image-file descriptors altogether. If an image inventory is wanted, fetch `images/index.json` and then only selected image-manifest/config descriptors; download image filesystem layers only when their contents are actually required. This is the layout inferred directly from Zarf’s constants and its one-file-per-layer assembly above, not a claim that an arbitrary OCI artifact follows this convention.

## UDS bundle layout (this checkout)

### Local bundle artifact

The UDS bundle builder first creates an OCI image-layout store, then writes a tarball containing `oci-layout`, `index.json`, the root-manifest/config blobs, `uds-bundle.yaml`, and the package blobs. Its root manifest is an OCI image manifest. `uds-bundle.yaml` is a `application/vnd.zarf.layer.v1.blob` layer titled `uds-bundle.yaml`; the root config is separately stored and the root descriptor is made the sole `index.json` entry. [UDS bundle construction](https://github.com/defenseunicorns/uds-cli/blob/1787dd331bb062c38df24373414e6bfece3c61c9/src/pkg/bundler/localbundle.go#L75-L78), [bundle YAML/config/root and layout entries](https://github.com/defenseunicorns/uds-cli/blob/1787dd331bb062c38df24373414e6bfece3c61c9/src/pkg/bundler/localbundle.go#L151-L184), [bundle YAML media type/title](https://github.com/defenseunicorns/uds-cli/blob/1787dd331bb062c38df24373414e6bfece3c61c9/src/pkg/bundler/localbundle.go#L239-L260).

Each selected Zarf package contributes its package-root manifest plus selected package blobs. The builder deliberately writes the OCI layout, UDS root manifest/config/YAML, then each package manifest and its small metadata blobs at the front of the tarball so `uds inspect` can stop its forward scan before image layers. This is an implementation optimization, not a general OCI archive rule. [UDS priority ordering](https://github.com/defenseunicorns/uds-cli/blob/1787dd331bb062c38df24373414e6bfece3c61c9/src/pkg/bundler/localbundle.go#L96-L100), [priority entries](https://github.com/defenseunicorns/uds-cli/blob/1787dd331bb062c38df24373414e6bfece3c61c9/src/pkg/bundler/localbundle.go#L186-L198).

### Remote bundle

The root bundle manifest’s layers include the package-root-manifest bytes as Zarf-blob layers. This deliberately non-obvious media type is historical compatibility behavior: UDS converts the package manifest descriptor to `application/vnd.zarf.layer.v1.blob` before appending it to the bundle root, rather than exposing it as a nested OCI image-manifest layer. [UDS remote bundle pusher](https://github.com/defenseunicorns/uds-cli/blob/1787dd331bb062c38df24373414e6bfece3c61c9/src/pkg/bundler/pusher/remote.go#L45-L81); [accepted ADR 0009](https://github.com/defenseunicorns/uds-cli/blob/1787dd331bb062c38df24373414e6bfece3c61c9/docs/adr/0009-bundle-media-types.md#L11-L22).

To inspect/select a bundled package, current UDS code fetches the package-manifest bytes from that root-layer descriptor, decodes it, fetches the `zarf.yaml` descriptor for component selection, and only then adds component layers and the selected nested-image descriptors to the pull set. [UDS bundle layer selection](https://github.com/defenseunicorns/uds-cli/blob/1787dd331bb062c38df24373414e6bfece3c61c9/src/pkg/utils/boci/oci.go#L330-L409), [metadata-layer selection](https://github.com/defenseunicorns/uds-cli/blob/1787dd331bb062c38df24373414e6bfece3c61c9/src/pkg/utils/boci/oci.go#L475-L499). The remote fetcher explicitly copies only descriptors selected by that process and skips layers already in its local store. [UDS remote fetcher](https://github.com/defenseunicorns/uds-cli/blob/1787dd331bb062c38df24373414e6bfece3c61c9/src/pkg/bundler/fetcher/remote.go#L68-L128).

## Recommendation: Neutrino’s bandwidth-minimizing retrieval plan

1. **Resolve, pin, and inspect the root before payloads.** For a remote reference, `GET` the tag manifest with an `Accept` set covering OCI index and image-manifest media types; retain/verify the returned digest. If it is an index, choose the required platform descriptor and fetch only that child manifest. For a local OCI-layout directory, read `index.json` and then only the selected root-manifest blob. Do not begin a recursive ORAS copy or a full archive extraction at this stage. [OCI Distribution pull rules](https://github.com/opencontainers/distribution-spec/blob/v1.1.1/spec.md#pulling-manifests); [OCI image layout](https://github.com/opencontainers/image-spec/blob/v1.1.1/image-layout.md).
2. **For a UDS bundle, fetch the minimum control plane.** Parse the root manifest, fetch its config if metadata is useful, then fetch the layer titled `uds-bundle.yaml` (and any required signature). Select package references from that YAML. For each selected package, fetch the package-manifest payload referenced by the bundle root as a layer blob and parse its descriptors. Neutrino must not assume that this bundled package manifest is available through the registry’s manifest endpoint: this UDS format intentionally labels it as a Zarf blob layer. [UDS bundle YAML layer](https://github.com/defenseunicorns/uds-cli/blob/1787dd331bb062c38df24373414e6bfece3c61c9/src/pkg/bundler/localbundle.go#L239-L260); [UDS package-manifest handling](https://github.com/defenseunicorns/uds-cli/blob/1787dd331bb062c38df24373414e6bfece3c61c9/src/pkg/utils/boci/oci.go#L335-L349).
3. **For a direct Zarf package or the decoded package manifest, classify descriptors by title and media type.** Fetch `zarf.yaml`, checksums/signature material required by the trust policy, and only the selected `components/...` chart/value/manifests/files descriptors. Explicitly defer every `images/blobs/sha256/...` descriptor. A title path is a Zarf layout convention, so treat it as a selection hint; verify the descriptor digest after every fetch. [Zarf per-file descriptors](https://github.com/zarf-dev/zarf/blob/v0.82.0/src/pkg/packager/layout/oci.go#L157-L165); [OCI descriptor integrity](https://github.com/opencontainers/image-spec/blob/v1.1.1/descriptor.md).
4. **Inspect Helm values at the least costly correct boundary.** If the selected Zarf component exposes a standalone values file, fetch that descriptor only. If it exposes a Helm chart archive (or an OCI Helm chart), first inspect its small OCI manifest/config, then fetch the one chart-content layer, decompress it, and read `values.yaml`; do not fetch provenance unless required. There is no standards-compliant smaller remote request for a file inside that gzip tar layer. [Helm media types](https://github.com/helm/helm/blob/v3.19.0/pkg/registry/constants.go); [Helm archive loader](https://github.com/helm/helm/blob/v3.19.0/pkg/chart/loader/load.go).
5. **Touch embedded image metadata only on demand.** To report images, fetch `images/index.json`, then selected image manifests/configs. To deploy or inspect a container filesystem, fetch its selected compressed image layers. Do not fetch any `images/blobs/sha256/...` entry merely because a package manifest lists it. The existing UDS selection logic demonstrates the same staged traversal. [UDS image-index and image-layer selection](https://github.com/defenseunicorns/uds-cli/blob/1787dd331bb062c38df24373414e6bfece3c61c9/src/pkg/utils/boci/oci.go#L363-L398).
6. **Handle local tarballs as streams, not remote registries.** For a UDS bundle tarball, read through the front-loaded metadata prefix and stop once the required root/package metadata and chart/value entries have been found; do not extract image files. For a generic Zarf archive, do not rely on member ordering—stream or index it until the desired members are reached. For an unpacked OCI layout, open only digest paths selected from the descriptor graph. Always re-hash fetched/extracted bytes before using them and preserve Zarf’s checksum/signature verification policy. [UDS tar priority ordering](https://github.com/defenseunicorns/uds-cli/blob/1787dd331bb062c38df24373414e6bfece3c61c9/src/pkg/bundler/localbundle.go#L186-L198); [OCI local layout](https://github.com/opencontainers/image-spec/blob/v1.1.1/image-layout.md).

### Limits to preserve in Neutrino’s design

* A manifest tells Neutrino the size, digest, media type, and (where Zarf supplies it) title of a blob; it does not expose the members of a compressed layer. Manifest-first inspection minimizes blob count and bandwidth but cannot eliminate transfer of a selected opaque chart/image layer.
* Index platform fields select manifest *variants*, not arbitrary files. A UDS/Zarf package can have an image index nested inside a package layer; discover it only if image metadata is needed.
* Registry API and layout rules do not replace artifact trust rules. Digest verification protects descriptor-addressed bytes; Zarf checksums/signatures remain necessary before accepting package metadata/content.
* In a remote UDS bundle, package manifest bytes are intentionally transported as a layer/blob for registry interoperability. Route those bytes through the blob/layer retrieval path even though their JSON parses as an OCI manifest.
